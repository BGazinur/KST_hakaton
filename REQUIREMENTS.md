# Требования AR Engineering

## Среда сборки

- Android Studio с поддержкой Android Gradle Plugin 9.2.1. Для Gradle нужен JDK 17 или выше. Сборка проверена с JDK 21 из Android Studio.
- Android SDK Platform 36 и Build Tools 36.0.0. Для установки через ADB нужен пакет Android SDK Platform-Tools.
- Gradle 9.4.1 запускается через включённый в проект Wrapper. Версии Kotlin, Jetpack Compose и ARCore закреплены в [app/build.gradle.kts](app/build.gradle.kts).
- Для первой сборки нужен доступ к Google Maven, Maven Central, Gradle Plugin Portal и Gradle Distributions. На телефоне для первичной установки или обновления сервисов AR может потребоваться интернет. Осмотр и пространственные метки должны работать локально после настройки.
- Сборка и Lint на Windows запускаются командой `.\gradlew.bat :app:assembleDebug :app:lintDebug`. На macOS и Linux используется `./gradlew :app:assembleDebug :app:lintDebug`.

## Устройство для проверки

- Физический Android-смартфон с Android 7.0 (API 24) или новее, поддержкой ARCore и установленными Google Play Services для AR. Нужны разрешение камеры и OpenGL ES 2.0.
- Depth API используется при поддержке устройством. На остальных устройствах используются обнаруженные плоскости или визуальные точки поверхности.
- Первую проверку проводить на неподвижном оборудовании с различимыми деталями при хорошем освещении. В ранее проверенном эмуляторе Pixel 8a экран разрешения камеры запускался. ARCore не смог открыть заднюю камеру этого виртуального устройства. Полевая проверка остаётся открытой.
- Официальные сведения о совместимости. [Требования AGP](https://developer.android.com/build/releases/agp-9-2-0-release-notes) · [Список устройств ARCore](https://developers.google.com/ar/devices) · [Настройка ARCore](https://developers.google.com/ar/develop/java/enable-arcore)

## Текущий этап — камера и ручная AR-метка

- Камера показывает живой видеопоток. ARCore совмещает визуальный трекинг с данными IMU телефона и пересчитывает позу камеры.
- По касанию приложение ищет точку на поверхности, ставит один 3D-якорь и рисует янтарную подсветку, стрелку и подпись. При новом успешном касании метка переносится. Её можно убрать кнопкой.
- При шаге вбок, приближении, смене ракурса и повороте экрана кончик стрелки должен оставаться на выбранной точке неподвижной детали.
- При паузе трекинга метка скрывается. При восстановлении действующего якоря она снова видна, когда точка в кадре. При окончательной потере якоря приложение предлагает поставить метку заново.
- Интерфейс следует [варианту B](docs/hud-reference.png). Камера занимает экран, голубая дуга и полупрозрачная карточка показывают статус, янтарный цвет выделяет отмеченный участок.
- Критерий приёмки этапа — повторить [проверку метки](Readme.md#проверка-метки) на физическом устройстве. Зафиксировать модель телефона, версию Android и результат для каждого движения.

## Следующий этап — интеграция модели

- Модель обучает отдельная команда. Перед интеграцией согласовать формат файла, классы, размер и формат входа, обработку кадра, формат выхода, координаты рамок или масок и пороги уверенности.
- Для отметки дефекта модель должна возвращать его местоположение. Для стрелки достаточно точки или рамки. Для подсветки по форме понадобится маска сегментации.
- Анализ должен идти локально в фоне на свежих кадрах. Перед размещением метки нужно преобразовать координаты с учётом поворота, обрезки и кадра анализа. Для 3D-привязки требуется точка на поверхности.
- Для первого сценария выбрать один вид оборудования и один визуальный признак с подходящими данными. Проверить размещение метки, задержку и поведение при потере трекинга. Ориентиры 4–5 классов оборудования, 2–3 вида дефектов и 5–10 анализируемых кадров/с взяты из исходного плана и требуют подтверждения на тестовом устройстве.
- Карточки оборудования, каталог и история осмотров относятся к последующим этапам. Решения о LiteRT, OpenCV, Room и отдельном режиме CameraX уточняются при появлении задач, для которых они нужны.
